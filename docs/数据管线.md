# 数据管线

把 13 份格式不一的原始文件，转成一张可查询的知识图谱。

源数据是一套真实工业档案的脱敏版本，保留了原始格式的混乱：省略的设备编号、不统一的分隔符、
同一部件在不同文档里的不同叫法。这份文档描述怎么把它清理干净、合并同名、建进 Neo4j，
以及怎么验证建对了。

---

## 总览

管线分四步，走完一遍产出可查询的图谱和一份对账报告。

```
data/raw/设备表备份_2026-09-23/      原始文件（7 个 xlsx + 6 个 docx）
        │
        │  ① 规范化  scripts/normalize.py      规则，确定性
        ▼
data/clean/*.json                    结构化中间产物
        │
        │  ② 归一    scripts/resolve.py        AI 出候选，规则拍板
        ▼
data/synonyms.json                   归一表（人工维护的资产，进仓库）
data/pending.json                    待确认队列
        │
        │  ③ 建图    scripts/build_graph.py   确定性
        ▼
Neo4j
        │
        │  ④ 对账    scripts/reconcile.py     确定性
        ▼
reports/reconcile.md                 差异报告
```

四步里只有第二步用到 AI。判断依据是：能写成规则的用规则，能算出来的用计数，
只有「这两个名字是不是指同一个东西」需要语义判断。

## ① 规范化

**输入**：13 个文件
**输出**：`data/clean/` 下 6 个 JSON，加一份处理报告

### 要处理的五类问题

| 问题 | 原始写法 | 处理后 |
|---|---|---|
| 编号省略前缀 | `tenlong-001、002、005、006` | 4 台独立设备 |
| 区间省略前缀 | `chengxin-001～006、025～030` | 12 台独立设备 |
| 「通用」后缀 | `tenlong/yuelong通用` | `['tenlong', 'yuelong']` |
| 分隔符不统一 | `、` `，` `/` 混用 | 统一成数组 |
| 规格嵌在名称里 | `硬质合金车刀片（CNMG120408）` | name=`硬质合金车刀片`，spec=`CNMG120408` |

第四类在前几项里都出现。第二类最容易出错：「chengxin-001～006、025～030」
后半段省略了前缀，只写数字区间，正则要维护前缀状态才能正确展开。

第五类只在备件表里，工具表的规格是独立列（如 `铜质Φ1.0`）。两个来源的规格位置不同，
统一到 `spec` 字段上才能合并成同一类节点。

### 自检

工艺流程图每格都标了台数，例如「tenlong-001～004（4台）」。展开后数量对不上就报错。

```
台数校验：流程1 4→12 ✓   流程2 4→8→12 ✓   流程3 3→6→12 ✓
          流程4 6→6 ✓    流程5 4→10→9→10 ✓  流程6 8→16 ✓
```

这条自检不是可选的。第一版解析器漏了省略前缀的分支，流程2 的 4 台被展开成 1 台，
边数会少一大截，而且不报错。

### 处理报告

每一步转换都记进 `normalize_report.md`，可追溯：

```
tenlong-001、002、005、006     → 展开 4 台     [编号省略前缀]
chengxin-001～006、025～030    → 展开 12 台    [区间省略前缀]
tenlong/yuelong通用            → 拆成 2 个      [通用后缀]
```

### 产物结构

```
equipment.json    {编号, 车间, 功能, 工具组[], 备件仓库, 是否检修, 重点标记}
spare_parts.json  {编号, 名称, 规格, 类别, 位置, 库存, 安全库存, 适用设备[], 备注}
repairs.json      {设备编号, 日期, 故障描述, 更换配件[], 使用工具[], 是否完成}
processes.json    {流程编号, 名称, 工序链[{序号, 设备批次, 设备编号[]}], 零件类型}
manuals.json      {型号, 故障表[{现象, 成因, 应急}], 备件处理[], 安全注意[]}
```

备件和工具合并成 `spare_parts.json`，用 `类别` 字段区分。两者在源数据里结构几乎一样
（都有编号、名称、规格、适用设备、备注），分开建节点会让 schema 复杂一层，
查询时还要记得两边都查。

合并后共 95 条：备件 46（三个仓库 18+18+10）+ 工具 49（五个工具组 9+9+6+9+8，含通用工具 8）。

## ② 归一

同一台部件在不同文档里有不同叫法。归一让这些叫法指向同一个节点，检修记录和手册的处理方法才能连起来。

### 实际遇到的例子

```
检修表：电磁吸盘失效
手册：  磁力吸盘失效        同一个东西，两个名字

检修表：轴承磨损
手册：  主轴轴承磨损        上下位关系，前者更宽泛
```

第二类不能简单合并。「主轴轴承磨损」比「轴承磨损」更具体，合并会丢信息；
不合并则查询要写两层。

### 分两段处理

**第一段：AI 生成候选。**

把三个名字列表合并后交给模型，让它找出可能指同一个东西的对：

```
检修表故障名 26 个 + 手册现象名 26 个 + 手册成因名约 25 个
```

输出带置信度和理由：

```json
[
  {"a": "磁力吸盘失效", "b": "电磁吸盘失效", "confidence": 0.95,
   "kind": "同义", "reason": "同一部件的两种叫法，均指磁性吸盘失去吸力"},
  {"a": "主轴轴承磨损", "b": "轴承磨损", "confidence": 0.6,
   "kind": "上下位", "reason": "前者是后者的具体化，可能应保留层级而非合并"}
]
```

**第二段：规则拍板。**

```
confidence ≥ 0.9        自动合并，写进 synonyms.json
0.6 ≤ confidence < 0.9  进 pending.json，等人确认
confidence < 0.6        不合并
```

### 待确认的处理

待确认的条目不进主图谱，单独标记：

```cypher
(:FailureMode {name:'熔渣堵塞', status:'待确认', source:'手册快速判断列'})
```

查询时过滤掉 `status = '待确认'` 的节点，不确定的数据不影响答案。

前端提供可点选的确认界面，把「合并 / 保留 / 跳过」的决策写回 `synonyms.json`。
这一步对应企业方案里的做法：

> 不一致的条目送入人工复核队列，标记为「待确认」。状态机不可调用「待确认」状态的参数。

### 用哪个模型

选 `qwen2.5-coder:14b`。它是个代码模型，而这一步做的是语义判断，看起来不匹配，
所以实测对比过通用模型：

| 模型 | 耗时 | 输出 | 候选 | 结果 |
|---|---|---|---|---|
| `qwen2.5-coder:14b` | 5.5 s | 99 tok | 2 组 | 正确 |
| `qwen3.8:27b-q5_k_m` | 77.8 s | 1024 tok | 0 组 | 截断，未产出 |

27B 的实际输出：

```
我们需要回答用户：从两组故障名称中找出跨两组之间可能指同一个东西的名称对。
要求输出 JSON 数组，只输出 JSON，不要解释。

任务：比较【检修记录里的故障名】和【故障手册里的……
```

它在用自然语言复述任务，然后把输入列表抄了一遍。检测显示输入列表的前 10 项
在它的输出里全部出现，1024 token 用尽还没到答案。

**失败的原因在输出格式，不在语义判断。** 代码模型被训练成给什么格式就输出什么格式，
通用模型倾向于先把思路讲一遍。这跟文献里「指令微调会导致过度健谈」的结论一致，
也跟查询链路上「thinking 模型把预算烧在推理上」是同一类问题。

27B 的生成速度是 13 tok/s，14B 是 78 tok/s。即使解决了格式问题，慢 6 倍也不划算。

### 需要人工判断的部分

源数据里超过半数的「错误」，根源是文本本身存在多种合理解读，解析失误只占少部分。
例如「喷嘴堵塞」的成因写成「熔渣堵塞」，两者既可能是同一件事的两种描述，
也可能是故障和成因的关系。这个判断需要懂机床的人做，规则和模型都替代不了。

## ③ 建图

按归一表把 5 个 JSON 写成 Cypher。全部用 `MERGE` 而不是 `CREATE`，保证脚本可以反复跑。

### 节点

| 标签 | 数量 | 来源 |
|---|---|---|
| `Equipment` | 127 | equipment.json |
| `SparePart` | 95 | spare_parts.json（备件 46 + 工具 49） |
| `WorkOrder` | 370 | repairs.json |
| `FailureMode` | 52 以内 | repairs + manuals，归一后合并 |
| `Process` | 6 | processes.json |
| `Operation` | 16 | processes.json 的工序 |
| `Location` | 17 | 车间 3 + 备件货架 14 |
| `Hazard` | 5 | 工具的高危标注 |
| `SafetyMeasure` | 若干 | manuals.json 的安全注意与应急处理 |

合计约 640 个节点。

### 关系

| 关系 | 数量 | 来源 |
|---|---|---|
| `(Equipment)-[:DEPENDS_ON]->(Equipment)` | 650 | 工艺流程推导 |
| `(Equipment)-[:EXPERIENCED]->(WorkOrder)` | 370 | 检修表 |
| `(WorkOrder)-[:CAUSED_BY]->(FailureMode)` | 370 | 故障描述 |
| `(WorkOrder)-[:USED_PART]->(SparePart)` | 564 | 更换配件 202 + 使用工具 362 |
| `(Equipment)-[:FITS]->(SparePart)` | 展开后数百 | 备件的通用设备 + 工具的适配设备 |
| `(Equipment)-[:IN_SHOP]->(Location)` | 127 | 分配单位 |
| `(SparePart)-[:STORED_AT]->(Location)` | 46 | 备件存放位置 |
| `(Process)-[:HAS_STEP]->(Operation)` | 16 | 工艺流程 |
| `(Operation)-[:PRECEDES]->(Operation)` | 13 | 工序链的相邻关系 |
| `(Operation)-[:USES]->(Equipment)` | 110 | 工序分配的设备 |
| `(FailureMode)-[:TRIGGERS]->(FailureMode)` | 待建 | 手册的成因列，需人工映射 |

### 库存字段带来的查询

备件表有 `库存数量` 和 `安全库存` 两列，这打开了一类之前做不了的问题。

**先说一个实测结果**：源数据里所有备件都合规，库存从未低于安全线，最小余量是 1。
所以「哪些备件低于安全线」返回空集，作为演示题没有区分度。
改成按余量排序才有意义：

```cypher
MATCH (p:SparePart)
RETURN p.name, p.stock, p.safety_stock,
       p.stock - p.safety_stock AS 余量
ORDER BY 余量 ASC LIMIT 5
```

实际会返回：刀架总成 4/1、伺服驱动器 3/1、电磁吸盘 3/1、激光切割头总成 2/1。
激光切割头总成余量只剩 1，是最紧张的。

**更有价值的是叠加影响面**：

```cypher
MATCH (p:SparePart)<-[:FITS]-(e:Equipment)
WITH p, count(DISTINCT e) AS 影响设备数,
     p.stock - p.safety_stock AS 余量
RETURN p.name, 余量, 影响设备数
ORDER BY 余量 ASC, 影响设备数 DESC
```

余量少且影响设备多的备件，是优先补货的对象。这是**二部图聚合加多字段排序**的组合，
传统 RAG 需要跨多条记录做集合运算，向量检索连数值比较都表达不了。

### 依赖边的推导

源数据没有直接给设备之间的上下游关系。工艺流程文档给了「工序链 + 每道工序分配到哪些设备」，
按相邻工序组两两相连展开：

```
流程2 盘套类件：车削 4 台 → 铣削 8 台 → 磨削 12 台
展开后：(4×8) + (8×12) = 128 条边
```

六条流程合计 650 条边。

**方向按「谁依赖谁」写。** `DEPENDS_ON` 的字面语义是「A 依赖 B」，下游工序消耗上游的来料，
所以边从**下游指向上游**：

```cypher
(下游设备)-[:DEPENDS_ON]->(上游设备)     -- 读作「下游依赖上游」
```

问「X 停机影响谁」就是找依赖 X 的设备：`(X)<-[:DEPENDS_ON*1..5]-(受影响设备)`。

> **方向写反过，代价很大。** 最初写成 `(上游)-[:DEPENDS_ON]->(下游)`，读起来成了
> 「上游依赖下游」。后果是问「huanmai-002 停机影响谁」返回的是它的 13 台**上游**设备，
> 而正确答案是 22 台**下游**磨削设备 —— 全错，但静态校验抓不到，
> 因为 `DEPENDS_ON` 两端都是 `Equipment`，自反关系任何方向在 schema 上都合法。

**这个展开隐含一个假设**：批次生产里同工序的设备可互换，上游工序的任何一台停机
都会拖累下游工序的所有设备。语义成立，但与「这台车床专供那台铣床」的精确上下游不同。

替代方案是加一个「工序步骤」中间节点，边数会少很多，代价是查询要多绕一跳。
选直接连边是因为查询简单，PageRank 也能直接跑。

### 覆盖情况

工艺流程覆盖 109 台设备。切割设备（heyue 18 台）不在其中，源文档说明了原因：
激光切割是独立下料工序，不属于车铣焊磨工序链。

后果是这 18 台在依赖网络里孤立：涉及上下游的问题问它们会返回空，PageRank 里全在最低分。

## ④ 对账

建完图后核对预期值与实际值。这一步决定前面三步有没有白做。

| 指标 | 预期值来源 | 不符意味着 |
|---|---|---|
| `Equipment` 节点数 | equipment.json 的 127 | 有设备没建上 |
| `WorkOrder` 节点数 | 370 | 有记录漏了 |
| `DEPENDS_ON` 边数 | 650 | 推导逻辑有 bug |
| `FailureMode` 节点数 | 归一后 ≤ 52 | 归一没生效 |
| 孤儿节点数 | 0 | 有断链 |
| 每条关系的两端标签 | schema 定义 | 建图写错了方向 |

### 对账的作用

企业方案里有一条数据：去掉关系嵌入后，准确率从 82.1% 暴跌至 18.4%。
图的价值集中在关系上，节点数对不代表关系建对了。

对账是唯一能发现归一遗漏的环节。归一漏掉一组同义词，边数就少一截，
其余环节察觉不到，只表现为「数据少一点」。这跟本项目在查询链路上踩过的坑同类：
一个致命的功能失效，表现得跟「效果差一点」一样。

### 报告形式

```
Equipment       127 / 127   通过
WorkOrder       370 / 370   通过
DEPENDS_ON      648 / 650   差 2 条
                排查：tenlong-004 在流程1、流程2 都出现，检查索引越界
FailureMode      49 / ≤52   通过（归一合并 3 组）
孤儿节点           0         通过
```

## 图谱 schema

9 类节点，11 类关系。相比最初的方案 C 设计，按实际数据做了三处调整。

### 调整

**去掉 `Role` 和 `Supplier`。** 源数据里没有岗位资质和供应商信息，留着会是永久空节点。

**`Tool` 并入 `SparePart`。** 备件和工具在源数据里结构几乎相同（都有编号、名称、规格、
适用设备、备注），合并后用 `category` 字段区分：

```cypher
(:SparePart {id:'A-001', name:'硬质合金车刀片', spec:'CNMG120408',
             category:'备件', location:'A区1号货架1层'})
(:SparePart {id:'通-001', name:'游标卡尺', spec:'0-150mm',
             category:'工具', stock:2})
```

**新增 `Process` 和 `Operation` 两个节点。** 工艺流程文档提供了六条工序链，
不建模就浪费了这批数据，而它正是依赖边的来源。

### 节点属性

| 标签 | 属性 |
|---|---|
| `Location` | name, kind（车间 / 货架） |
| `Equipment` | id, model, function, shop, inspected, priority |
| `SparePart` | id, name, spec, category, location, stock, safety_stock, note |
| `WorkOrder` | id, date, done |
| `FailureMode` | name, status, source |
| `Process` | id, name, part_type |
| `Operation` | name, order |
| `Hazard` | name, level |
| `SafetyMeasure` | name, text |

`FailureMode` 的 `status` 用来标记归一后的确定程度，取值为 `确认` 或 `待确认`。
`source` 记录这条是从哪个文件抽出来的，便于回溯。


待确认队列做成真交互：点「合并」写回 `synonyms.json`，「跳过」写入 `pending_skipped`，
操作后图谱局部刷新。对应接口：

```
GET  /pipeline/status      各步状态与统计
GET  /pipeline/pending     待确认队列
POST /pipeline/resolve     {a, b, action}  action: merge | keep | skip
GET  /pipeline/graph       图谱数据（前端可视化用）
```

这样做的价值在于，「人工复核不可省略」从一条原则变成了可操作的界面。
企业方案里说系统应「将真正需要人工判断的条目筛选出来，而非追求全自动的 100% 准确率」，
这个界面就是那个筛选动作的落点。
